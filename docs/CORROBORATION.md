# instl Docs — Corroboration Against Waves Central

Cross-check of the instl documentation set against the Waves Central repo (`ProAudio/XPlatform/CopyProtect/wls/Central`, branch `feature/V17.0.10---POC-Download-Enhancements`), which embeds instl as its install engine. Generated by the `corroborate-instl-docs-with-central` workflow; doc corrections were applied in place.

## Evidence sources (Central)

- **Waves Central: how it builds, ships, and invokes the instl tool** — Waves Central (Electron app, package.json version 17.0.10) ships three instl engines: a PyInstaller-built "latest" bundle (instl.bundle, onedir) plus two checked-in legacy executables instl-V9 and instl-V10. The latest engine is built from the instl repo (cloned/checked-out branch download-enhancements) by running instl itself on Build-index.yaml (`instl doit --in Build-index.yaml --out build-instl.py --run --no-system-log`), which invokes PyInstaller via instl.spec (build_instl.py -> build_python.build_onedir). On Mac the bundle is signed with codesign (hardened runtime, timestamp, entitlements) per-file then bundle-wide. At runtime the bundle lives under "Waves Central.app/Contents/Resources/res/external/bin/instl.bundle/Contents/MacOS/instl" (Win64/instl.exe on Windows); legacy engines live directly in .../bin/instl-V9|V10. Central's TypeScript ShellInstl layer builds per-action YAML inputs and drives instl through subcommands (synccopy, sync, copy, uninstall, report-versions, exec, doit/run-process, version). Online actions inject access params (base_links_url, cookie_jar, REPO_REV_EXT) into the YAML; the standalone Python scripts (reportVersions.py, install_cen.py, organizer.py) read config var __INSTL_LAUNCH_COMMAND__ to build their own instl invocations.
- **instl YAML input contract (Waves Central production data)** — The Waves Central production data dir confirms DOMAIN.md's core model with high fidelity. The index (index-V10.yaml, 512KB) is a multi-document YAML: a sequence of !define / !define_Mac / !define_Win / !define_Win32 / !define_Win64 documents establishing config vars (paths, curl tunables, reusable action macros, and template texts) followed by a single `--- !index` document at line 558. Every documented IID field is exercised in real items: name, guid, version, phantom_version, install_sources, install_folders, inherit, depends, actions, remark, direct_sync, previous_sources, info_map, plus per-OS sub-mappings (Mac, Win, Win32, Win64). Template instantiation uses exactly the `TemplateName<arg1,arg2,...>:` form with a list-of-arg-lists body, matching read_index_template_node. The full action_types vocabulary appears (pre/post_sync absent here, but the whole pre/post_copy[_to_folder/_item], remove_item, pre/post_remove[_from_folder/_item], and a doit phase in download_doit.yaml/testInstl.yaml are all present). Driver files compose via `__include__` and `__include_if_exist__`, and conditionals __ifndef__/__ifdef__ and __environment__ are used at file scope. Two notable gaps in DOMAIN.md: (1) the `__include__` map-form (url:/copy:/checksum: keys for remote-fetch-then-cache includes) is heavily used but undocumented; (2) `direct_sync` appears as a per-IID list value `- $(VAR)`, not just a boolean flag.
- **Download System Enhancement (Central POC) — corroboration of instl download subsystem mapping** — The Download System Enhancement is an in-flight POC (Central branch feature/V17.0.10---POC-Download-Enhancements; instl branch download-enhancements) that upgrades Waves Central + instl so interrupted/lossy/slow network installs complete more often, waste less bandwidth, and produce diagnosable, classified failures without compromising integrity. It is sequenced as 7 milestones/phases: M0 baseline+capability discovery, M1 atomicity/temp+checksum-before-promotion, M2 safe byte-range resume, M3 classified retry policy, M4 adaptive parallelism, M5 Central UX, M6 controlled rollout (cohorts/flags). Central docs define a canonical session and per-file state machine that matches instl's downloadState.py enums exactly (DownloadSessionState/DownloadFileState), a unified failure taxonomy that matches downloadFailures.py's DownloadFailureClass, plus resume sidecars, a stdin control channel (pause/resume/try_now), client-side offline-grace detection, between-session adaptive concurrency, and a redacted DOWNLOAD_EVENT structured channel. The non-negotiable invariants center on: never trust partial files as cache, manifest SHA1 (not S3 ETag) is final integrity authority, verified-only final cache paths, and capability-gated UX. Critically, decision D-022 records that the POC branch intentionally ships Central UX on-by-default (violating D-004/D-005) and MUST be re-gated before merge to main; D-023 drops the "repairing" visual sub-state in v1. The instl docs/REFACTORING.md proposes W2/W3/W7 that directly touch this active download subsystem and would conflict if done concurrently.
- **Testing & QA for the download-system enhancement (Central + instl)** — The download subsystem is tested with a full pyramid: Python unittest suites in instl (test_downloadState/Promotion/Retry/Observability/Concurrency/Events/Cohort/Failures/ControlChannel) and Jest suites in Central (errorParsers, progress handler, statistics). instl owns planning/transfer/retry/resume/verification/promotion/state/events; Central owns orchestration, UX, error->action mapping, and compatibility parsing. The test strategy explicitly demands integrity-before-speed, deterministic unit-testable state transitions, and resume tests covering unsafe server behavior (200-instead-of-206, identity change, expired signed URL), not just the happy path. Telemetry is emitted as single-line "DOWNLOAD_EVENT <json>" plus legacy "DOWNLOAD_RETRY_DECISION <json>" lines, both privacy-redacted via a fixed denylist, and observability writes download-state/session-summary.json. The test-strategy names coverage gaps: network-simulation tests (latency/loss/throttle/DNS/TLS/429/5xx), soak tests, and manual-QA scenarios are listed as planned/required but show no recorded "Test Evidence" runs, and Central UX telemetry events are explicitly "Planned — NOT yet emitted." A detailed manual-QA resume playbook exists because resume cannot be distinguished from restart-from-zero by eye, requiring log-side evidence and a negative-control run.
- **Waves Central documentation - how Central describes instl (the install engine) and the overall system** — Central's own docs describe it as a multi-process Electron desktop app (main / renderer / splash) built on a Strategy + Singleton + Decorator pattern foundation, where instl is one of the "Native tooling payloads" / "external payloads" used as the install engine. Central never reimplements install logic: it shells out to the bundled `instl` binary via a Strategy-pattern wrapper (`instlWrapper` -> `ShellInstl` behaviour) that builds `instl <subcommand> --in/--out/--log/--run` command lines. instl appears as a black-box CLI invoked for install/repair/update/remove/report-versions, and the three Python scripts (organizer.py, install_cen.py, reportVersions.py) are instl batch/exec scripts shipped in `buildResources/data` that Central feeds to instl. Central's terminology differs from instl's: Central speaks of "install engine", "behaviours", "central processes", and "repositories/repo-rev"; the instl client/admin/GUI persona split is NOT visible in Central's docs — Central only ever drives the instl CLI as a single launch command (`__INSTL_LAUNCH_COMMAND__`) plus a `--config-file locations.yaml`, with `runAsAdmin`/elevation handled by Central, not by an instl "admin persona". This corroborates instl's architecture as a CLI install engine but suggests instl's "personas" abstraction is internal to instl and not surfaced (or used) by its primary consumer.
